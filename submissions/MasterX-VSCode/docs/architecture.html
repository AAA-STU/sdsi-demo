MasterX · architecture

A cheap model reads the code. An expensive one only reads its notes.

MasterX is a VS Code extension that runs two separate claude CLI processes on different models. The Worker does the high-volume reading and writing. The Master only plans and reviews, so it spends tokens on reasoning instead of source files.

System map

Everything runs on your machine except the model calls. The panel is plain HTML in a webview. The extension host owns the run. Each model call is a fresh, one-shot claude -p child process that talks to the gateway.

ChatViewProvider

Receives execute, stop and set-model from the panel. It loads the config, writes the per-run settings file, builds the Worker, Master and Orchestrator, runs the goal, and deletes the settings file in a finally block. A second goal is refused while one is running.

Orchestrator

The only code that touches the workspace. It scans files, calls the Worker and Master in order, writes files with workspace.fs, and runs commands in a visible terminal. It reports every step back through log, stage and summary hooks.

Worker and Master

Thin wrappers. Each builds a system prompt, calls runClaudeCli with a fixed tool list, and parses the answer. The Master's plan is checked against a JSON schema and again in code before anything runs.

Child processes

Spawned without a shell, with --print --output-format json --no-session-persistence. Each call is independent, so nothing is remembered between calls except what the extension passes in the prompt.

One run, stage by stage

Pressing Execute starts four stages. The orange arrow is the point of the design: the Master receives the Worker's summary and nothing else about your code.

  1. Index Worker

    The host lists up to 400 files (skipping node_modules, out, .git and similar) and reads the first 2,000 characters of up to 12 text files. The Worker turns that into a dense architectural summary.

    in goal, paths, samples
    out summary text

  2. Plan Master

    The Master reasons about the goal against the summary and returns JSON: a thought and an ordered list of tasks. Each task has an action, a targetPath and self-contained instructions.

    in goal, summary
    out MasterPlan (validated)

  3. Execute Worker

    For each task the Worker drafts the complete file, or a single command line in cmd.exe syntax on Windows. The host writes the file or runs the command in a terminal and captures the exit code.

    in task instructions (+ current file for edits)
    out file text or one command

  4. Report Master

    The Master reads the goal and the per-task results, then writes a plain report: what was done, what failed, what to do next. It appears in the panel console.

    in goal, results
    out final report

Where the models and key come from

Each value is resolved by taking the first match from top to bottom. The config panel and the status line show the exact source that won.

Master model

  1. masterx.masterModel (set by the dropdown)
  2. model in ~/.claude/settings.json
  3. ANTHROPIC_MODEL
  4. built-in claude-opus-5-5

An alias like opus expands through ANTHROPIC_DEFAULT_OPUS_MODEL.

Worker model

  1. masterx.workerModel (set by the dropdown)
  2. CLAUDE_CODE_SUBAGENT_MODEL
  3. ANTHROPIC_DEFAULT_HAIKU_MODEL
  4. built-in claude-haiku-5-5

Settings file first, then the process environment, at each step.

API key

  1. masterx.openAiApiKey
  2. OPENAI_API_KEY
  3. ANTHROPIC_AUTH_TOKEN

The last step is why a fresh install works: your gateway token already lives in ~/.claude/settings.json.

Catalog URL

  1. masterx.modelListUrl
  2. https://creditclaim.reskilll.com/llm/v1/models

Fetched once per panel and cached for the dropdowns. If it fails you can type a model id.

  2. Saved to settingsmasterx.masterModel or workerModel, workspace scope when a folder is open
  3. Run startsloadConfig() resolves both ids and the key
  4. Run file writtentemp settings.json, mode 0600
  5. Each callclaude --settings <file>, merged over your global file
Run-scoped settings file (only the overrides) 
// %TEMP%\masterx-run-settings-<stamp>.json, deleted when the run ends
{
  "model": "<Master model>",
  "env": {
    "CLAUDE_CODE_SUBAGENT_MODEL": "<Worker model>",
    "ANTHROPIC_AUTH_TOKEN": "<key>",
    "ANTHROPIC_API_KEY": ""
  }
}

The CLI merges env key by key, so the gateway base URL and everything else still come from ~/.claude/settings.json. That global file is never written to. ANTHROPIC_API_KEY is blanked so an empty inherited value cannot shadow the token.

What each model call is allowed to do

Every call gets an explicit tool list. Only the indexing call can read files, and it cannot write or run anything.

Guardrails, and where it is thin

What holds

  • Files stay in the workspace. Every task path is resolved against the workspace root, and anything that escapes it is refused.
  • Tools are an allow-list per call. The Master and all drafting calls have none. Indexing is read-only.
  • Stop works. The abort signal reaches the child process, the command poller, and the loop between tasks.
  • Calls are bounded. Each has a timeout, output is capped, and no session is kept after a call.
  • Your global config is untouched. Only a temp file is written, and it is deleted in a finally block.

What to know

  • Commands run without a confirmation step. The Master picks a command, the Worker writes the line, and the extension runs it in a terminal. Read the plan in the console if the task touches anything you care about.
  • The key sits in a temp file during a run. It is removed afterwards, but a crash of the host mid-run could leave it behind.
  • The plan is only as good as the summary. Sampling is alphabetical and capped at 400 paths and 12 file heads, so a large repo reaches the Master as a sketch.
  • The plan is checked for shape, not sense. The schema and parser confirm each task is well formed, not that it is a good idea.
  • Failed tasks do not halt the run. Later tasks may build on something that was never written.
